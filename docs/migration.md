# Project metadata and migration

## `.bwenv.toml` in v2.4

When `bwenv init` has a stable folder ID, it writes a versioned `.bwenv.toml` alongside `.envrc`.
This file is project configuration and can be committed with the project:

```toml
version = 1
provider = "bitwarden"

[project]
folder_id = "abc123"
folder_name = "Production"
items = ["item-id-a", "item-id-b"]

[activation]
mode = "direnv"
```

The file stores provider references and activation settings, not secret values or session tokens.
New projects include `folder_id`; migrated older projects may omit it and use the slower folder-name
lookup until they are reinitialized.

Generated `.envrc` files load this metadata with `bwenv export --project .`. The direct
`--provider`, `--folder`, `--folder-id`, and `--items` flags remain available for scripts and CI.

Existing projects continue to work without `.bwenv.toml`: bwenv reads their generated `.envrc`
settings. If a `.bwenv.toml` file exists but is invalid or uses an unsupported version, bwenv
reports the error instead of silently using potentially stale `.envrc` metadata.

To migrate an existing generated project, inspect the preview and then apply it:

```bash
bwenv migrate --dry-run
bwenv migrate
```

Migration writes `.bwenv.toml`, replaces the provider-specific export command with
`bwenv export --project .`, and retains the original `.envrc` as `.envrc.bwenv.bak` with mode
`0600` where POSIX permission bits are supported. The backup is ignored by Git through the existing
`*.bak` rule; keep it until the migrated project has been verified. A dry run creates neither the
backup nor the new config.

The migration accepts `.envrc` files generated by bwenv. It stops without changing files if it
finds custom shell commands or ambiguous session assignments, so those can be reviewed manually.
The current v2 login and export flow still relies on `BW_SESSION` in `.envrc`; migration preserves
that line rather than breaking activation. Moving runtime sessions out of project files is deferred
until the v3 session-management work.

## Upgrading from v1

The original v1 project used Makefile, Bash, and PowerShell scripts. The current v2 application is
a Go binary, introduced to provide consistent cross-platform behavior and native support across
operating systems. Install the current release, then run `bwenv init` in each project to generate
its current activation files. See the
[v1 migration steps in the README](../README.md#migration-from-the-original-version).
